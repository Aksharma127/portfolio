What it does

docqa answers questions about a folder of PDFs, text files and Markdown notes. Nothing is sent to an external service: embedding, vector search and the language model all run on the local machine. Each answer lists the source file, page and section of the chunks it used, so it can be checked.

It has a Python API and a command-line interface.

How data moves through it

  1. ExtractPyMuPDF for PDFs; TXT and Markdown with encoding fallbacks; page and section kept
  3. ChunkRecursive splitter with overlap
  5. Embedall-MiniLM-L6-v2 (384-dim), cached in SQLite
  7. StorePersistent ChromaDB collection, cosine similarity
  9. RetrieveTop-k semantic search (k = 5 by default)
  11. AnswerQwen2.5-1.5B-Instruct via llama.cpp, with an answer cache

Design decisions

Index by content hash

Every file is tracked by its SHA-256 hash. Re-running the indexer skips unchanged files, re-indexes modified ones and removes chunks for deleted ones, so a large folder doesn't get re-embedded on every run.

Keep provenance on every chunk

Chunks carry file, page and section metadata from extraction onward. The answer can then cite exactly where it came from instead of just returning text.

A small quantized model

Qwen2.5-1.5B in Q4_K_M is about 1 GB, so it runs on an ordinary laptop. The model file is configurable for bigger machines.

Persistent caches with a known limit

Both caches are SQLite and survive restarts. SQLite allows one writer at a time, which is fine for a single-user tool and is documented as the trade-off.

Testing

Unit tests cover chunk boundaries and overlap, encoding fallbacks and malformed PDFs in the extractors, the indexer's add, update, skip and delete paths, cache persistence, and RAG context building.
